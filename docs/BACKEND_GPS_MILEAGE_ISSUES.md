# CarGPS 后端 GPS 与里程问题说明

记录日期：2026-08-03  
适用范围：当前生产后端 `positionSave`、设备位置表、设备及保养项目里程累计逻辑  
问题来源：设备 `866275035374421` 实际里程与平台里程差异核查

## 1. 背景与结论

设备 `866275035374421` 本阶段车辆仪表里程为 `8974 km`，平台
`device.current_mileage` 为 `7430.803 km`，少计 `1543.197 km`，误差约
`17.20%`。

使用现有后端过滤规则重新计算得到 `7431.330 km`，与数据库累计值只差约
`0.527 km`。因此本次问题不是简单的数据库加法错误，而是以下问题共同造成：

1. App 端断网积压、缓存损坏和定位异常造成原始 GPS 缺失；
2. 后端对历史补传、乱序点和并发点缺少可靠结算机制；
3. 低速、短距离等过滤条件偏保守；
4. GPS 入库、设备里程和项目里程缺少事务、幂等及补偿能力；
5. 时间单位、实时状态和历史补传数据没有严格分离。

本文只描述后端问题、预期结果和验收标准。App 侧问题见
`V1.1.2_GPS_RELIABILITY_ISSUES.md`。

## 2. P0：必须优先修复

### SERVER-01 历史补传点入库，但没有补算里程

**问题位置**

`Index.php::positionSave()` 每次查询数据库中 `position_time` 最大的记录作为上一点。
当数据库已经有更晚的实时点，再收到较早的历史补传点时，计算得到的时间差小于或等于
0，里程过滤返回无效，但该 GPS 点仍然会被保存。

**当前行为**

- 历史 GPS 能够进入位置表；
- `device.current_mileage` 和 `project.current_mileage` 不增加；
- 轨迹看似已经补齐，但平台里程没有补回；
- 后续重复补传因为位置点已存在，也无法自动修复遗漏里程。

**预期结果**

- 原始 GPS 与里程结算解耦；
- 每台设备按照原始 `position_time` 顺序结算；
- 历史补传完成后，自动对受影响时间段重新结算；
- 同一补传区间重复结算不得重复增加里程；
- 记录补传批次、结算状态和结算水位。

### SERVER-02 GPS 入库和里程累计不在同一事务

**问题位置**

当前处理依次执行：保存 GPS、增加设备里程、增加项目里程、更新速度和时间。这些操作是
相互独立的数据库操作，没有统一事务或可靠的异步结算记录。

**当前行为**

- GPS 保存成功，但设备里程可能更新失败；
- 设备里程更新成功，但部分项目里程可能更新失败；
- 请求重试时可能因为 GPS 已存在而提前返回；
- 已经出现的不一致没有自动补偿入口。

**预期结果**

- 原始 GPS 先可靠持久化；
- 由结算任务生成唯一 `settlement_batch_id`；
- 设备里程、项目里程和结算明细在同一事务中更新；
- 失败批次可安全重试；
- 重复执行同一批次只能产生一次里程增量。

### SERVER-03 同一设备并发和乱序处理导致多算或少算

**问题位置**

同一设备的多个请求可以同时执行“查询上一点、计算距离、插入 GPS、累加里程”。后端没有
设备级串行队列、锁或结算水位。

**当前行为**

- 两个请求可能读取同一个上一点并分别累计，造成重复计算；
- 较晚点先处理后，较早点的时间差变成负数，造成漏算；
- 相同 GPS 数据在不同到达顺序下可能得到不同总里程。

**预期结果**

- 同一设备必须按采集时间串行结算；
- 不同设备允许并行处理；
- 乱序点先进入原始库，再由消费者排序结算；
- 相同输入数据无论请求顺序如何，最终里程结果必须一致。

### SERVER-04 数据库缺少强唯一约束

**问题位置**

- `device_position` 只有普通索引，没有
  `UNIQUE(device_no, position_time)`；
- `device.device_no` 没有唯一索引；
- 当前使用“先 SELECT、再 INSERT”进行应用层查重，存在并发竞态。

**当前行为**

- 同一设备同一时间可能产生多条位置记录；
- 并发首次上传可能创建重复设备；
- 默认保养项目可能重复创建；
- 设备里程可能被分散到不同设备记录中。

**预期结果**

- `device.device_no` 建立唯一索引；
- `device_position(device_no, position_time)` 建立唯一索引；
- 保养项目增加符合业务规则的唯一约束；
- 重复请求返回幂等成功，不重复入库和计程；
- 自动创建设备必须正确处理唯一键冲突。

### SERVER-05 GPS 时间单位混用

**问题位置**

上传接口把 13 位毫秒时间转换成 10 位秒时间保存；轨迹查询接口却使用 13 位毫秒范围查询，
并将位置时间差再次除以 1000。数据库字段注释也与实际保存单位不一致。

**当前行为**

- 轨迹接口可能查询不到位置记录；
- 同一秒内多个点失去精确顺序；
- 同秒去重可能误判；
- 时间差、速度及距离计算口径不一致；
- 补传、实时状态和监控系统可能采用不同时间单位。

**预期结果**

统一字段定义：

- `position_time`：设备原始 GPS 采集时间，13 位毫秒；
- `received_at`：服务器接收时间，13 位毫秒；
- 原始采集时间一经接收不得修改；
- 查询、排序、去重和计算统一使用毫秒；
- 历史秒级数据迁移时增加明确的版本或单位标记。

### SERVER-06 跨日历史点被改写成服务器当前时间

**问题位置**

当前代码在 `position_time` 早于服务器当天零点时，直接使用 `time()` 覆盖原始采集时间。

**当前行为**

- 昨日缓存点在次日补传时被伪装成当前点；
- 大量历史点可能集中到相同或相近秒；
- 破坏轨迹顺序、同秒去重和里程计算；
- 历史速度、坐标可能污染实时速度、当前位置和在线状态。

**预期结果**

- 原样保存可信的 `position_time`；
- 使用 `received_at` 表示服务器实际接收时间；
- 时间明显异常时增加 `time_invalid` 标记，不静默改写；
- 历史点只进入原始轨迹和历史结算，不更新实时状态。

### SERVER-07 低速和不足 5 米的真实位移被永久丢弃

**问题位置**

当前里程规则直接过滤：

- 当前速度小于 `3 km/h`；
- 相邻点距离小于 `5 m`。

在 1 Hz 上传频率下，每秒 5 米相当于约 `18 km/h`。

**当前行为**

堵车、停车场、厂区、缓慢起步和低速行驶产生的小位移被逐点丢弃，后续不会补回。
4421 的可用 GPS 轨迹与平台累计之间约有 `237.4 km` 差异，低速和短距离过滤是主要因素。

**预期结果**

- 不再把每个不足 5 米的点直接永久丢弃；
- 以最后计程锚点为基准累计连续小位移，达到阈值后统一计入；
- 静止场景结合 `accuracy`、卫星数、定位来源和点位聚类过滤漂移；
- 非法经纬度和超过物理上限的跳点继续硬过滤；
- 记录每段里程的接收或过滤原因。

### SERVER-08 超过 5 分钟的断档直接计 0

**问题位置**

两个位置点间隔超过 300 秒时，当前规则直接不计算该段里程，也不产生业务异常记录。

**当前行为**

- 断档期间的实际行驶全部表现为 0；
- 客户只看到平台里程偏少；
- 系统无法区分车辆静止、关机、断网、缓存未补传或 GPS 无效；
- 补传完成后没有自动重新结算入口。

**预期结果**

- 不直接使用断档两端直线距离补里程；
- 创建 `mileage_gap`，记录设备号、起止时间、两端坐标和断档时长；
- 补传完成后自动关闭断档并重新结算；
- 无法补齐的断档进入人工校准清单；
- 对连续 10 分钟无有效点进行监控告警。

### SERVER-09 历史补传污染当前速度和在线状态

**问题位置**

当前每收到一个位置点，包括历史点和重复点，都会更新 `last_speed`、`last_speed_time` 和速度
缓存，没有判断传入点是否比现有实时状态更新。

**当前行为**

- 补传昨日数据时可能展示昨日速度；
- 在线状态与当前速度相互矛盾；
- 历史坐标可能被当成当前位置；
- 补传期间实时状态可能来回跳变。

**预期结果**

- 只有 `position_time >= 当前 last_speed_time` 且采集时间未过期时，才更新实时状态；
- 历史补传只写原始轨迹和历史结算；
- 页面当前速度超过规定时间后显示 0 或未知；
- 可单独展示“补传中”和待补传时间范围。

### SERVER-10 GPS 上传接口缺少设备身份认证

**问题位置**

当前控制器无需登录，位置上传只依赖请求中的 `device_no`，设备不存在时还会自动创建正式设备和
默认项目。

**当前行为**

知道设备号的人可能伪造 GPS、速度和里程，重放历史请求，或者批量创建垃圾设备和项目。

**预期结果**

- 每台设备使用独立密钥；
- 请求包含时间戳、随机数和内容签名；
- 服务端校验时间窗并防止重放；
- 增加设备和 IP 频率限制；
- 未授权设备不得自动创建正式业务数据。

## 3. P1：建议同步修复

### SERVER-11 设备里程和项目里程可能不一致

**问题位置**

`device.current_mileage` 和各项目 `project.current_mileage` 分别保存并分别更新。

**当前行为**

任一更新失败都可能造成设备总里程和保养项目里程不同，不同页面显示不同结果。

**预期结果**

- 优先以设备总里程作为统一主值；
- 项目保存启用时的设备里程基线，通过差值计算项目使用里程；
- 如果继续保存项目累计值，必须与设备里程在同一事务更新；
- 增加定期一致性检查和自动修复任务。

### SERVER-12 缺少里程结算明细和重算能力

**问题位置**

系统只保存最终累计值，没有保存每个区间的里程增量、过滤结果、过滤原因和结算批次。

**当前行为**

出现误差后无法快速说明哪一段被计入、过滤或遗漏，规则调整后也无法安全重算。

**预期结果**

增加里程结算明细，至少包含：

- `device_no`；
- `from_position_time`、`to_position_time`；
- `distance`；
- `result`：`accepted/rejected/gap`；
- `reason`；
- `settlement_batch_id`；
- `created_at`。

支持按设备和时间段重算，并能够与当前累计值自动核对。

### SERVER-13 在线时间与移动时间混用

**问题位置**

`last_time` 主要在产生有效里程增量时更新。车辆静止时即使持续上传，也可能不更新该字段。

**当前行为**

静止但正常上报的设备可能显示离线，在线状态不能准确反映设备连接和 GPS 状态。

**预期结果**

分别保存：

- `last_received_at`：最近收到请求时间；
- `last_position_time`：最新 GPS 采集时间；
- `last_movement_time`：最近有效移动时间；
- `last_mileage_time`：最近里程结算时间。

在线状态不得依赖是否产生里程。

### SERVER-14 整数里程字段产生累计取整误差

**问题位置**

设备和项目的 `current_mileage` 使用整数米，Haversine 计算结果包含小数米。

**当前行为**

逐点累加时会产生取整误差。4421 按后端规则重算与数据库累计相差约 `0.527 km`，该问题不是
本次主要原因，但会长期积累。

**预期结果**

- 使用 `DECIMAL(16,3)` 保存米，或统一保存毫米整数；
- 只在接口展示时换算并四舍五入为公里；
- 中间计算和结算明细保留统一精度。

### SERVER-15 原始位置质量字段不足

**问题位置**

当前位置表没有保存定位精度、卫星数、定位来源、服务器接收时间、补传状态和过滤原因，经纬度还使用
字符串字段。

**当前行为**

后端只能依靠经纬度和速度做粗略判断，难以可靠区分真实移动、弱定位、静止漂移和历史补传。

**预期结果**

- 原始 GPS 写入 TDengine 并至少保留 7 天；
- 保存 `accuracy`、卫星数、定位来源、`position_time`、`received_at`；
- 经纬度使用合适的数值类型；
- 原始点与里程结算结果分开保存；
- 支持算法调整后重新计算。

### SERVER-16 单个 GPS 请求的数据库操作过多

**问题位置**

每个位置点当前需要执行设备查询、查重、查询上一点、位置插入、设备更新、项目更新和缓存更新等多次
操作。

**当前行为**

设备数量扩大后，MySQL 写压力和锁竞争会快速增加；接口变慢后又会反向造成 App 补传队列积压。

**预期结果**

- 上传接口只完成鉴权、校验和可靠入队；
- GPS 高频原始点批量写入 TDengine；
- 按设备和批次结算有效里程；
- MySQL 只保存低频累计结果和业务项目数据；
- 结算延迟、失败批次和积压量必须可监控。

## 4. Redis、TDengine、MySQL 改造约束

建议链路：

```text
GPS上传
→ 鉴权与基础校验
→ Redis可靠队列/Stream
→ 按设备和position_time排序
→ 批量写TDengine原始点
→ 生成里程结算批次
→ 事务更新MySQL设备及项目里程
→ 记录结算明细
→ 成功确认并清理Redis
```

必须满足：

1. Redis 数据成功写入 TDengine 后才能确认原始点持久化完成；
2. TDengine 成功但 MySQL 失败时必须能够重新结算；
3. 每个批次有唯一编号，重复消费不得重复增加里程；
4. 同一设备按采集时间串行结算；
5. 行程结束未触发时，仍有 1～5 分钟周期结算；
6. Redis TTL 只能作为兜底，不能早于数据持久化和结算完成；
7. Redis 开启符合风险要求的持久化，消费者使用确认和待处理机制；
8. 原始点至少保留 7 天，里程明细保留时间不得短于业务审计周期。

## 5. 验收标准

1. 相同 GPS 数据重复上传 2 次、10 次，里程只能增加一次；
2. 同一批 GPS 按顺序、倒序、随机顺序上传，最终里程必须一致；
3. 实时点已经存在后再补传历史点，补传区间里程能够正确重新结算；
4. GPS 入库成功、MySQL 更新失败后，系统可以自动重试并恢复一致；
5. 设备里程和所有启用项目里程保持业务一致；
6. 跨日补传保留原始采集时间，不污染当前速度、位置和在线状态；
7. 3～18 km/h 低速行驶不得因单点不足 5 米而长期不累计里程；
8. 注入 `(0,0)`、100 km 级跳点和 200 米低精度点，不得造成里程虚增；
9. 连续 30～50 km 路测，平台与车辆仪表误差不超过 3%，调优后目标不超过 2%；
10. 连续 10 分钟无有效点、结算积压和消费失败必须产生告警；
11. 3000、4000、5000、6000 请求/秒压测时，GPS 接收、TDengine 持久化和 MySQL 结算分别统计
    成功率、P95/P99、积压量和数据一致性；
12. 压测结束后，原始点数量、唯一点数量、结算批次数和累计里程能够完整对账。

## 6. 建议实施顺序

1. 统一 `position_time` 单位，增加 `received_at`；
2. 增加设备和位置唯一约束；
3. 建立可靠原始 GPS 入库及幂等批次；
4. 实现同设备串行的历史补传与里程重算；
5. 实现设备、项目和结算明细的一致性更新；
6. 调整低速、小位移和静止漂移算法；
7. 分离历史补传状态与当前速度、在线状态；
8. 增加断档、积压、失败批次和里程差异监控；
9. 增加设备签名、防重放和频率限制；
10. 完成路测、断网补传测试及阶梯压测后再上线。
