## 2. P0：下个版本必须修复

### P0-1 使用 JSON 全量文件作为实时队列，性能随积压量恶化

当前每个 GPS 点都会执行多次线性查找、全量排序和完整 JSON 重写；上传成功一条后也会再次完整重写。定位回调频率约为 1 Hz，队列达到数千条后会持续占用主线程和闪存 IO，上传回调无法及时执行，形成“队列越大、上传越慢、积压继续扩大”的正反馈。

修复：

- 使用 Room/SQLite 保存待传点。
- 以 `(device_no, position_time)` 建立唯一索引。
- 新点只执行单条 INSERT，成功后只执行单条 DELETE。
- 所有队列操作放到单独的串行 IO Executor，不在定位线程或主线程读写数据库/文件。
- 查询按 `position_time ASC`，每次只读取下一批记录，禁止每点全量排序。
- 设置队列容量、数据库大小和最老记录时间监控，但不得静默丢弃。

### P0-2 队列文件非原子写入，损坏后直接丢失积压点

`FileWriter` 直接覆盖正式文件。写入期间进程退出、断电或并发写入会留下不完整/错误格式文件。`loadPendingGps()` 解析失败后只记录日志，未保留损坏文件、未恢复备份，下一次写入会覆盖原始积压数据。

修复：

- Room/SQLite 事务替代 JSON 文件。
- 若迁移阶段仍需 JSON：写入 `.tmp`，`flush + fsync` 后原子 rename，并保留 `.bak`。
- 解析失败时将文件改名为 `.corrupt.<time>`，禁止覆盖；尝试从 `.bak` 恢复并上报告警。
- 增加旧版 JSON 到 Room 的一次性迁移和异常格式兼容。

### P0-3 日志系统同步 IO 过重，直接阻塞 GPS 处理

`LogUtil.writeToFile()` 每条日志都打开、写入并关闭文件；每写 10 条又调用 `cleanExpiredLogs()`，该方法会读取并重写整个当前日志文件。当前每个 GPS 点会产生多条日志，现场日志达到数 MB 后，这一逻辑会持续阻塞调用线程。

修复：

- 使用单独日志线程和缓冲写入。
- 过期清理改为每天/启动后后台执行一次，不能每 10 条执行。
- 轮转检查按时间或文件大小低频执行。
- 正式版只记录状态变化、失败、周期汇总；禁止每秒打印完整 GPS 和完整响应体。
- `SimpleDateFormat` 不跨线程共享，或改用线程安全时间格式化。

### P0-4 GPSDialog 存在永久观察器、重复网络上传和无界列表

- `mCurrentLocation.observeForever()` 和 `createTrackResult.observeForever()` 没有注销。
- 每次重新打开 Dialog 可能新增永久观察器，导致同一点被重复处理。
- `GPSDialog` 仍每秒调用 `uploadSpeed()`；`positionSave` 已包含速度，这个请求重复且会争抢网络资源。
- `locationMsgList` 每秒增加且不限制数量，并对整个 RecyclerView 调用 `notifyDataSetChanged()`。
- `ServiceIdManagerUtil.uploadLog` 每次速度响应都追加，未设置上限。

修复：

- GPSDialog 只显示速度，不发送任何 GPS/速度请求。
- 改用生命周期感知 Observer，或在 dismiss/onStop 中 removeObserver。
- UI 只保留最近 100 条展示数据，使用 `notifyItemInserted()`。
- 内存上传日志设置固定上限，或完全移除。

### P0-5 Service 销毁时资源没有完整释放

`RunAppService.onDestroy()` 只注销了网络 Receiver，没有停止 AMap 定位、销毁定位客户端、移除 Handler 定时任务，也没有注销 `tryCreateTrack.observeForever()`。服务重启后可能残留旧回调或定时任务，增加重复上传和内存泄漏风险。

修复：

- `stopLocation()`、`onDestroy()` 定位客户端。
- `handler.removeCallbacksAndMessages(null)`。
- 注销全部永久 Observer。
- 取消或标记失效所有网络 Call 和上传任务。

### P0-6 历史补传会污染“当前速度/在线状态”，跨日旧点还会被改写为当前时间

记录日期：2026-07-22。

触发场景：车机无网期间持续采集 GPS 和速度，恢复网络后按照原始 `position_time` 从旧到新补传。

当前行为：

- `positionSave()` 每接收一个点（包括重复点）都会直接覆盖 `device.last_speed` 和 `device.last_speed_time`，没有判断该点是否比当前缓存更新。
- 同日历史点补传时，`getDeviceSpeed()` 因“超过 10 秒返回 0”的保护通常不会把旧速度显示成实时速度，但设备表中的速度缓存仍被历史点反复覆盖。
- 后端把早于服务器当天 0 点的 `position_time` 直接改成 `time()`。跨日补传时，历史位置和历史速度因此会被伪装成当前数据。
- GPS Monitor 当前按 `id DESC` 取最后入库点并直接展示其速度，因此同日补传期间也会展示历史速度；在线状态可能同时显示离线，形成“有车速但设备离线”的矛盾状态。
- 跨日点被改写为当前时间后，养车秘书和 GPS Monitor 都可能错误显示历史车速、当前位置和在线状态，同时破坏轨迹顺序、同秒去重和里程计算。

修复：

- 服务端必须原样保存可信的 GPS `position_time`，禁止使用接收时间静默替换跨日历史点。
- 新增独立 `received_at`/`server_received_time` 字段表示服务器实际收到时间，采集时间与接收时间不可混用。
- 只有传入点的 `position_time >= device.last_speed_time` 时才允许更新 `last_speed`、`last_speed_time` 和当前坐标缓存；历史补传只入轨迹表，不覆盖实时状态。
- 对明显错误的设备时间单独标记 `time_invalid` 或拒绝进入实时状态缓存，保留原始值供追查，不得改写成当前时间。
- 增加“补传中”状态或待传数量，UI 将“历史点速度”与“当前速度”分开显示；当前速度超过 10 秒必须显示 0 或未知。
- GPS Monitor 的最新位置查询改为 `ORDER BY position_time DESC, id DESC`，并在 `position_time` 过期时不展示为当前车速。

涉及代码：

- 后端 `Index.php::positionSave()`：跨日时间改写，以及无条件更新 `last_speed/last_speed_time`。
- 后端 `Index.php::getDeviceSpeed()`：10 秒过期保护。
- GPS Monitor `server/app.py::get_latest_position()`：当前使用 `ORDER BY id DESC`。
- GPS Monitor `js/app.js::updateDeviceInfo()`：当前无条件展示返回点的 `speed`。

### P0-7 设备 866275035374421 实际里程与平台里程相差 1543.197 km

记录日期：2026-07-31。

对比口径：

- 车辆仪表本阶段里程：`219884 - 210910 = 8974 km`。
- 平台 `device.current_mileage`：`7430803 m = 7430.803 km`。
- 少计：`1543.197 km`，约占车辆实际里程的 `17.20%`。
- 数据库位置记录区间：2026-07-15 11:42:33 至 2026-07-31 15:06:44。
- 上述比较以仪表起始值 210910 km 与本轮数据清理起点一致为前提；若起点时间不一致，需要重新校准比较口径。

核查结论：

- 位置表共 653618 行、653611 个唯一 `position_time`，仅 7 条同秒重复；重复数据不是本次少计的主要原因。
- 按当前后端规则完整重算得到 `7431.330 km`，与数据库累计值只差约 `0.527 km`。这说明数据库累计和加法逻辑基本一致，不是简单的累计字段算错。
- 排除超过 5 分钟的断点连接和超过 200 km/h 的明显异常跳点后，可用 GPS 轨迹约为 `7668.224 km`。
- 相对仪表里程，约 `1305.8 km` 来自 GPS 缺点、长断档、缓存读取失败及定位异常；该数值是按现存数据估算，缺少原始点的历史路段无法精确回算。
- 在可用轨迹基础上，后端低速、短距离等业务过滤进一步少计约 `237.4 km`。
- 共发现 123 个不少于 10 分钟的断档。典型断档为 2026-07-22 21:28:08 至 2026-07-23 06:04:20，持续约 8 小时 36 分钟。
- 断档前 App 日志显示待传队列曾达到 2451、3495 条；后续重启时出现
  `Expected BEGIN_ARRAY but was STRING`，随后 `service_start` 队列为 0，证明部分已采集待传点没有从缓存恢复。
- 日志还出现定位精度 150～200 米、经纬度 `(0,0)` 和约 109 km 的瞬时跳变。6 个计算速度超过 200 km/h 的明显异常跳点合计产生约 534.6 km 虚假直线距离，这部分必须过滤，不能作为真实缺失里程补回。
- 当前逐点规则会排除速度低于 3 km/h 的点和相邻距离不足 5 米的点。按 1 Hz 上传计算，5 米阈值相当于约 18 km/h，容易少计堵车、停车场、缓慢起步和低速行驶。

处理：

App 侧：

- 使用 Room/SQLite 事务队列替代 `pending_gps.json`，落实 P0-1、P0-2，禁止解析失败后把待传队列静默当作空队列。
- 增加损坏数据隔离、备份恢复和告警；任何恢复失败的队列文件必须保留，不能被新点覆盖。
- 增加批量补传接口或批量上传机制，补传吞吐量必须稳定高于实时新增的 1 点/秒；记录新增速度、补传速度、队列长度和预计排空时间。
- 上传 `accuracy`、定位来源、卫星数量等质量字段，区分真实移动、弱定位和静止漂移。
- 首次定位、重启恢复及定位源切换时增加连续点确认，避免错误的首点成为过滤锚点，导致后续真实点被长时间判定为跳变。

后端侧：

- 保留经纬度非法、计算速度超过物理上限等硬过滤，禁止直接把大断点两端用直线距离补成里程。
- 将“单点距离不足 5 米直接丢弃”改为小位移累计：以最后计程锚点为基准累计连续位移，达到阈值后一次计入，避免每秒低速位移永久丢失。
- 将固定的速度、距离阈值改为结合时间差、定位精度、卫星数和连续点趋势判断；静止场景使用聚类/漂移半径过滤。
- 对超过 5 分钟的断档记录 `mileage_gap`、起止时间和两端坐标，进入异常清单，不静默计 0，也不直接连接计算。
- 若车机可以读取仪表/CAN 总里程，应以车辆总里程作为累计基准，GPS 里程用于校验；检测到差值超限时告警并进入人工校准流程。
- 历史已经缺失且日志中也没有原始坐标的路段，不能依靠算法精确恢复。本次历史差额应经客户确认后按车辆仪表做一次里程校准，并保留校准前值、校准值、时间和原因。

客户沟通口径：

- 平台累计程序重算结果与数据库基本一致，不属于数据库随机少加。
- 差异主要由部分行驶时段没有留下连续可用的 GPS 点，以及现有防漂移规则对低速行驶过滤偏保守共同造成。
- 历史缺少原始点的路段只能按车辆仪表校准；新版本通过可靠缓存补传和计程规则调整，解决后续继续少计的问题。

## 3. P1：建议同版本一起修复

### P1-1 上传状态机缺少可靠的周期重试和退避

- 单条失败会结束本轮上传。
- 主要依赖新 GPS 点、网络广播或 30 分钟定时器再次触发。
- `CONNECTIVITY_ACTION` 在新 Android 版本上可靠性有限。

修复：使用 `ConnectivityManager.NetworkCallback`，并由独立上传器按指数退避重试；有待传数据时设置较短重试周期，成功后连续排空，失败后退避并保留记录。

### P1-2 单点串行协议吞吐缺乏余量

每秒生成 1 点，若平均单次请求耗时接近或超过 1 秒，队列必然增长。建议增加后端批量位置接口，一次按时间顺序提交 50～200 点并逐批确认。若暂不改后端，至少保证网络请求和回调不在主线程，并记录每分钟上传吞吐量与新增量。

### P1-3 日志上传可能并发，且未校验业务成功码

- 服务启动、网络恢复和定时器都可能同时调用 `uploadDeviceLog()`，现场 14:28 同一时刻产生了两个 ZIP。
- `onResponse()` 不检查 HTTP 状态和业务 `code`，收到失败响应也会删除 ZIP 并清理全部本地日志。

修复：增加单实例上传锁；只有 HTTP 成功且业务 `code=0` 时才删除对应 ZIP；日志快照上传成功后只删除快照覆盖的文件，避免清除上传期间新产生的日志。

### P1-4 设备开机时间可能错误

现场重启初期系统时间显示为 2026-01-15，网络恢复后才校正为 2026-07-15。离线启动时生成的日志时间和 GPS 时间可能异常；后端当前会把早于当天的 `position_time` 改成服务器当前时间，可能破坏原始顺序并制造同秒冲突。

修复：App 检测墙上时钟可信度；时间未同步时保留 GPS 原始时间、elapsedRealtime 和采集顺序，不直接上传为可信业务时间。服务端后续也应避免静默改写原始时间。

### P1-5 发布版网络 BODY 日志过多

OkHttp 使用 `HttpLoggingInterceptor.Level.BODY`，每秒请求会产生大量序列化和 Logcat 输出。正式版改为 NONE/BASIC，仅在诊断开关开启时记录必要字段。

### P1-6 数据库仍缺少强唯一约束

当前后端先 SELECT 再 INSERT 去重，竞态下仍出现了 2 条完全相同的同秒记录。建议后端最终增加 `(device_no, position_time)` 唯一索引，并将重复键视为幂等成功。

### P1-7 补传期间缺少实时数据与历史数据的可观测性

目前无法从页面或监控接口确认设备是在实时上传，还是正在快速补传数小时前的缓存点。建议上报和监控以下字段：队列长度、最早/最新待传时间、采集时间、服务端接收时间、补传状态、补传吞吐量。设备在线应由最新可信采集时间判断，网络连接状态可由最近接收时间单独表示，二者不得共用一个“在线”字段。

## 4. v1.1.2 验收测试

1. 连续在线运行 3 小时：队列长期接近 0，数据库原始时间连续，App 主线程无明显卡顿。
2. 断网 10 分钟：本地应积累约 600 个唯一点；断网期间强制重启 App/设备，队列数量应完整保留。
3. 恢复网络：按原始时间顺序补齐，队列持续下降并最终清空；补传速度必须高于 1 点/秒。
4. 在队列为 100、1000、10000 条时分别测试入队耗时、内存、CPU 和磁盘占用，入队不能随总量线性恶化。
5. 上传过程中强制断电：重启后数据库/队列均保持一致，不出现文件解析失败或静默清空。
6. 重复打开/关闭 GPSDialog、反复锁屏解锁：观察器数量、速度请求数和定位回调数不能增长。
7. 日志接口返回 HTTP 500、业务 `code != 0`、DNS 失败、超时：本地日志不得删除。
8. 新版本时段同秒重复率目标低于 1%，连续 30 分钟唯一点接近 1800，无 10 分钟断档。
9. 选择 30～50 km 实际路测，数据库唯一轨迹重算距离与真实里程对比；轨迹完整后再判断后端里程过滤是否需要调整。
10. 同日断网 10 分钟后恢复：补传期间当前速度应保持 0/未知或显示“补传中”，不得把历史速度标成实时速度；数据库原始 `position_time` 必须保持不变。
11. 跨 0 点断网并在次日恢复：昨日缓存点必须保留昨日原始时间，不得被改写为服务器当前时间；设备在线状态不得因历史补传而误判在线。
12. 补传期间同时查询养车秘书与 GPS Monitor：两端当前速度、在线状态和最新位置判断应一致；队列排空后应在 10 秒内恢复为真实实时状态。
13. 使用车辆仪表作为基准执行连续 30～50 km 路测，正常道路场景平台里程误差应不超过 3%；完成参数调优后目标不超过 2%。
14. 增加拥堵和低速场景测试，持续以 3～18 km/h 行驶时不得因单点不足 5 米而长期不累计里程。
15. 断网积压不少于 3000 点后重启 App/设备，待传记录必须完整恢复；联网后补传速度持续高于新增速度并最终排空。
16. 注入经纬度 `(0,0)`、150～200 米低精度点、100 km 级跳点和静止漂移，异常点不得导致里程虚增，恢复正常定位后不得长期卡在旧坐标锚点。

## 5. 当前处理建议

- 暂停继续扩大 v1.1.1 安装范围。
- 已安装设备可继续观察，但发生长队列时不要主动重启，否则可能触发队列文件解析失败并丢失积压点。
- 保留服务器上的设备日志 ZIP。即使数据库缺点，日志仍可能用于还原部分轨迹和缺失里程。
- v1.1.2 完成上述 P0 后先在单台设备执行断网、重启、恢复网络测试，再扩大部署。
